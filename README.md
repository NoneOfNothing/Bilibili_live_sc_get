# Bilibili_live_sc_get（blive_sc_get）

监听 B 站直播间的弹幕 WebSocket 通道，自动抓取 **SuperChat（醒目留言 / SC）** 并保存到本地。支持多房间同时监听、断线自动重连、重启后去重，并记录 SC 被删除（退款）的事件。

协议实现参考了以下开源项目对现行 web 端弹幕协议的梳理（本项目代码为独立实现）：

- [xfgryujk/blivedm](https://github.com/xfgryujk/blivedm) —— Python 弹幕库（WBI 签名、认证包格式参考）
- [simon300000/bilibili-live-ws](https://github.com/simon300000/bilibili-live-ws) —— Node.js 弹幕库
- [AsaChiri/DDRecorder](https://github.com/AsaChiri/DDRecorder) —— 录制工具（SC 落库思路）

## 功能

- 自动获取真实房间号（支持短号和直播间链接）
- 接入弹幕服务器：自动处理 WBI 签名、游客 buvid3、brotli 压缩报文
- 抓取 `SUPER_CHAT_MESSAGE`（含日文翻译版 `SUPER_CHAT_MESSAGE_JPN`）与删除事件 `SUPER_CHAT_MESSAGE_DELETE`
- JSONL 保存完整原始数据，CSV 保存关键字段（Excel 直接打开）
- 心跳保活 + 超时检测 + **带随机抖动的指数退避重连**（重试间隔 1 秒起、上限 30 秒；静默断网约 50 秒内被发现，短暂断网会自动恢复并输出可观测日志）；重启后自动跳过已保存的 SC
- CSV/JSONL 被占用（如 Excel 打开 CSV）时自动进入重试队列，每 5 秒补写；中途退出重启后也会恢复队列继续补写
- 房间级互斥锁：同一房间不会被多个实例重复监听，避免并发写入损坏数据
- 一个进程可同时监听多个直播间
- `--auto` 自动跟随浏览器（**实验性**）：扫描 Edge/Chrome 会话，把浏览器里打开的直播间自动加入监听（每 30 秒重扫，动态新增、不自动停止）。该实现方式存在明显局限，**日常使用推荐 GUI 启动方式手动管理房间**，详见[自动检测](#自动检测浏览器里的直播间auto)一节
- 图形界面：房间管理（添加/删除/启停）、实时标题、房间备注、历史 SC 查看 + 实时显示、**可选弹幕显示与按日落盘**、**发送弹幕与直播间专属表情包**、**点击弹幕正文复制**、翻阅历史时的新消息浮动计数、**粉丝牌等级与任务查看（含按房间手动/自动完成点赞与发弹幕）**、**浏览器扩展一键获取登录 Cookie（无需关闭浏览器）**、**房间独立窗口（右键单开只显示该直播间 SC 与弹幕的窗口，一房一窗可并存）**、调试日志页签

## 快速开始

需要 Python 3.9+。

```bash
# 方式一：手动安装
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt      # Windows
.venv/bin/pip install -r requirements.txt          # Linux / macOS

# 监听单个房间（可粘贴直播间链接），Ctrl+C 停止
.venv\Scripts\python main.py 直播间号

# 监听多个房间、指定输出目录和日志文件
.venv\Scripts\python main.py 直播间号1 直播间号2 -o data --log-file logs/sc.log
```

Windows 下也可以直接**双击 `start_sc_get.bat`**（首次运行自动建虚拟环境装依赖；默认监听房间 1727071052，可在文件里修改，或从命令行传其他房间号）。

**多开**：复制 `start_room_模板.bat` 并重命名为 `start_room_你的房间号.bat`，把里面的「房间号」替换成实际直播间号，双击即可启动一个独立实例窗口（窗口标题带房间号），**无需拷贝整个项目文件夹**。含房间号的启动脚本已被 `.gitignore` 排除，不会提交到 git。

**自动跟随浏览器（实验性，不推荐）**：双击 `start_auto.bat`（或命令行 `python main.py --auto`），程序扫描 Edge/Chrome 当前打开的标签页，自动监听其中所有 B 站直播间。⚠️ 该功能实现方式依赖对浏览器磁盘快照的字节扫描，可靠性有限（见下文说明），**日常使用建议改用 GUI 启动方式**（`start_gui.bat`），在界面中添加/启停直播间更直观可控。技术细节见[自动检测](#自动检测浏览器里的直播间auto)一节。

### 参数说明

| 参数 | 说明 |
| --- | --- |
| `ROOM ...` | 房间号（必填，可多个，支持短号/链接） |
| `-o, --output-dir` | 数据保存目录，默认 `data` |
| `--cookie` | B 站 cookie 字符串，见下文 |
| `--duration 秒数` | 运行指定秒数后自动退出（0 表示一直运行） |
| `--log-file 路径` | 同时把日志写入文件 |
| `-v, --verbose` | 调试日志（所有消息类型、人气值等） |

## 输出格式

```
data/
  room_直播间号/
    sc_直播间号.jsonl     每日完整记录，一行一条 JSON
    sc_直播间号.csv       每日关键信息，utf-8-sig，Excel 可直接打开
    deleted_ids.json      被删除（退款）的 SC id -> 删除时间
    pending_records.jsonl 因文件被占用暂未写入的记录（补写成功后自动删除）
    .room_lock            房间互斥锁（进程退出自动释放，文件残留无害）
```

JSONL 中一条 SC 记录（`sc` 字段保留了 B 站推送的完整原始数据，含头像、勋章、背景色等）：

```json
{"type": "sc", "time_received": "2026-09-06T20:15:30", "room_id": 114514,
 "sc": {"id": 123456, "price": 30, "message": "主播加油", "start_time": ..., "end_time": ..., "user_info": {"uname": "..."}}}
```

CSV 列：`sc_id, price_cny, username, uid, message, start_time, end_time, duration_sec, received_time`。

删除事件会追加写入当天 JSONL（`"type": "delete"`）并登记进 `deleted_ids.json`；CSV 为追加式记录，不回改历史行。

写入失败自动重试：若 CSV/JSONL 被其他程序占用（如用 Excel 打开 CSV），该条记录会进入 `pending_records.jsonl`，程序每 5 秒自动补写（只补缺失的部分，不产生重复行），补写成功后该文件自动删除；程序中途退出也没关系，重启连接房间后会先恢复队列继续补写。

## 什么时候需要 cookie？

程序默认以游客身份抓取：会自动获取游客 `buvid3` 并对弹幕接口做 WBI 签名，多数情况足够。如果日志出现 `-352 / -403 / -412`（风控），需要提供**已登录**的 cookie：

1. 浏览器登录 bilibili.com，按 F12 打开开发者工具 → Network（网络）→ 刷新页面 → 任选一个请求 → Request Headers → 复制整行 `Cookie:` 的值；
2. 三选一：
   - 保存为项目根目录的 `cookie.txt`（推荐，注意该文件已被 .gitignore 排除）；
   - 设置环境变量 `BILI_COOKIE`；
   - 命令行 `--cookie "..."`。

cookie 只用于读取弹幕连接 token，请注意保管，不要泄露或提交到仓库。

**GUI 一键获取**：房间列表底部有「获取Cookie」和「从插件获取」两个按钮。

- **「从插件获取」（推荐）**：使用自带的浏览器扩展，**无需关闭浏览器、不受新版 App-Bound 加密影响**。首次使用前先在浏览器安装扩展：
  1. 打开 `edge://extensions`（Chrome 用 `chrome://extensions`），开启右上角「开发者模式」；
  2. 点「加载已解压的扩展」，选择本项目的 `extension/` 目录；
  3. 在程序里点「从插件获取」，程序会在本机回环 `127.0.0.1:64321` 短暂开启接收窗口；
  4. 点浏览器工具栏上的插件图标，勾选「我了解风险并发送」后点「获取并发送」，程序即收到并写入 `cookie.txt`、应用到当前会话（约 90 秒未收到会自动关闭等待，可重试）。

  安全：插件只读取 `bilibili.com` 域的登录 Cookie（含 `SESSDATA`、`bili_jct`，**等同你的登录凭证**），且**只发送到本机 127.0.0.1 的本地端口、不会上传任何网络**；程序仅绑定回环地址、校验请求来源必须是浏览器扩展（普通网页无法伪造）、只有在你主动点击时才开启该窗口。请注意保管 Cookie，不要在不可信环境使用。

- **「获取Cookie」（备用）**：从本机浏览器的 Cookie 数据库读取 bilibili.com 的 Cookie。支持 Edge / Chrome / Brave / Vivaldi / Opera / Firefox（正在运行的浏览器优先，自动选择可用的 Cookie；带 SESSDATA 的已登录 profile 优先）。限制：
  - 新版浏览器**运行时会独占锁定 Cookie 数据库**，获取时可能需要暂时完全退出对应浏览器再重试；
  - 新版 Chrome/Edge 的 App-Bound 加密 Cookie（v20）暂无法解密，遇到时会明确提示；
  - 若均失败，仍可按上文手动复制 Cookie。

## 应用配置文件（config.json）

项目根目录的 `config.json` 存放**应用级行为开关**（与界面设置 `data/gui_rooms.json` 无关）。
该文件**不随仓库分发**（含个人开关）：**首次运行程序**（GUI 或命令行）时若不存在会**自动生成**带字段说明的默认配置，可随时删除，下次运行按需重建：

```json
{
  "allow_write_operations": false,
  "emoticon_tooltip": {
    "text": true,
    "unique": false,
    "id": false
  },
  "medal_tasks": {
    "auto": false,
    "like_interval_sec": [15, 20],
    "danmaku_interval_sec": [6, 8],
    "max_retry": 3
  },
  "logging": {
    "enabled": false,
    "level": "INFO",
    "file": "logs/app.log",
    "max_bytes": 2097152,
    "backup_count": 3,
    "categories": {
      "room": true,
      "window": true,
      "data": true,
      "task": true,
      "live": true,
      "app": true
    }
  },
  "preview": {
    "quality": 0,
    "mute": true,
    "volume": 60,
    "always_on_top": true,
    "follow_room": true
  }
}
```

- `allow_write_operations`：**写操作总开关**（发送弹幕、自动点赞等会向 B 站提交数据的操作）。
  出于安全考虑**默认关闭**；程序默认只读，只有在文件中显式改为 `true` 后相关功能才会启用。修改后需**重启程序**生效。
- `emoticon_tooltip`：鼠标**悬浮表情**（表情面板里的表情、或弹幕区里的表情图）约 0.5 秒时提示哪些字段（Qt 版弹幕里的表情已直接显示为图片，提示只补文字）。
  可写成对象（如上）或列表 `["text", "unique", "id"]`，字段含义：
  - `text`：触发词（如 `[百岁山]`）
  - `unique`：表情唯一标识（如 `room_9527_109824`，即发送表情包弹幕时实际提交的 `msg`）
  - `id`：数字 `emoticon_id`

  **默认仅 `text`**；写空列表 `[]` 或全部 `false` 表示不显示提示。修改后需**重启程序**生效。
- `medal_tasks`：**粉丝牌自动任务**配置（见下文[粉丝牌任务](#粉丝牌任务)）。
  - `auto`：**全自动总开关**（同时约束点赞与发弹幕两项），默认 `false`。开启后仍需在界面「粉丝牌」页签里对**具体房间**分别勾选「自动发弹幕」/「自动点赞」，且 `allow_write_operations` 必须为 `true`，满足后才会后台自动执行。
  - `like_interval_sec` / `danmaku_interval_sec`：两次点赞 / 发弹幕之间的**随机间隔秒数**（数组 `[最小, 最大]`）。
  - `max_retry`：单个写任务连续失败多少次后停止本轮（避免失败重试风暴）。
- `logging`：**运行日志**（Tk 版、Qt 版与命令行**共用**同一套设置），用于事后监测运行状态——GUI 常常是静默启动（`start_gui_silent.vbs` / `pythonw`，没有控制台），那种场景下只有落盘的日志能回溯「昨晚为什么掉线」这类问题。
  - `enabled`：是否把日志**写入文件**，默认 `false`（日志照常显示在 GUI「调试」页、命令行照常输出到控制台，只是不额外落盘）；需要长期监测运行状态时改为 `true`。
  - `level`：**启动级别**，可选 `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL`（默认 `INFO`，大小写不敏感）。写在 GUI 里勾选「显示 DEBUG 日志」可**临时**提升为 DEBUG（取消勾选即回到这里配置的级别，不会改动配置文件）。
  - `file`：日志文件路径，默认 `logs/app.log`；**相对路径按项目根目录**解析（也可写绝对路径）。
  - `max_bytes` / `backup_count`：单个文件大小上限（字节，默认 `2097152` = 2 MB）与保留的历史文件数（默认 3）——超出即轮转，形如 `app.log`、`app.log.1`、`app.log.2`……不会无限增长。
  - `categories`：**分区块日志开关**，六块**默认全部 `true`**：
    | 区块 | 覆盖内容 |
    |------|---------|
    | `room` | 房间与选择：切换直播间、添加/删除、启停监听、排序、拖动排序、备注、点击跳转 |
    | `window` | 界面布局：窗口尺寸、分隔条、页签切换、弹幕区/表情面板显隐、调试日志开关 |
    | `data` | 数据读写：接口请求、历史 SC 读取与落盘（弹幕按批汇总）、表情包 / 弹幕选项 / 粉丝牌刷新 |
    | `task` | 任务与写操作：发送弹幕与表情、粉丝牌任务（手动/自动/打断）、Cookie 获取、开播提醒 |
    | `live` | 直播连接与状态：WS 连接与重连、开播下播、SC 与弹幕接收、房间锁占用 |
    | `app` | 应用生命周期：启动退出、配置加载、后台就绪/失败、调试日志级别 |

    **判定顺序：先看主开关 `enabled`（只决定是否落盘），再看区块开关**——区块设为 `false` 后，该类日志在控制台、GUI「调试」页与文件里**都不输出**；未标记区块的第三方库日志不受影响。只想盯关键信息时可关掉噪音较大的区块（如 `{"room": false, "window": false, "data": false}`，只看任务与连接）。
  - **覆盖范围**：接口请求会记录「路径 + 房间号/uid/分页等关键参数 + 耗时 + 返回 code」（**不记录 cookie、csrf 与 WBI 签名**）；窗口尺寸与分隔条拖动这类高频事件会**节流合并**成一条「首次 → 最后」的日志，拖动时不会刷屏；弹幕落盘按批汇总（不逐条记，避免刷爆日志）。
  - 文件日志**带完整日期**，每条都含级别与来源模块（如 `Room[房间号]`、`gui.room`），程序启动时会先把「日志级别 / 落点 / 区块开关状态」写进日志，方便确认配置是否生效。
- `preview`：**直播预览**的默认值（仅 Qt 版；Tk 没有可用的视频组件，见下文[直播预览](#直播预览仅-qt-版roadmap-63)）。
  - `quality`：清晰度，**默认 `0` = 自动**（取该房间可用最高档）；也可固定成 `80`（流畅）/`150`（高清）/`250`（超清）/`400`（蓝光）/`10000`（原画）/`20000`（4K）/`30000`（杜比）。实际可用档位取决于**房间与账号**：浮窗下拉会按拉流接口返回的可用档位收缩（例如该房间没有 4K 就不会出现「4K」），未登录只有 360P / 720P 两档。
  - `mute`：是否默认静音（默认 `true`，避免切换直播间时突然出声）。
  - `volume`：音量 0–100（默认 `60`，取消静音后生效）。
  - `always_on_top`：预览浮窗是否置顶（默认 `true`）。
  - `follow_room`：是否让预览跟随主界面选中的直播间（默认 `true`）——**只把该房间设为「主路」（有声音的那一路），不会增删预览的路数**；选中的房间不在预览中时什么都不做。
  - `max_rooms`：同时预览的路数上限（`1`~`4`，默认 `4`）；到达上限后再加入会被拒绝并提示。
  - `max_drift_sec`：允许的**播放落后**秒数（默认 `3`，写 `0` 关闭）——直播播放比网页端每分钟约慢 0.1~0.2 秒，累计超过这个值就自动重新拉流跳到最新画面（见下文[直播预览](#直播预览仅-qt-版roadmap-63)一节）。
  - `watch_time`：是否在预览播放时上报「观看时长」（**写操作**，默认 `false`）——还需 `allow_write_operations` 为 `true` 并已登录才会真正生效，详见下文预览一节。
  - **未登录（无 Cookie）时 B 站只给到 720P**：程序会把清晰度下拉收缩成 360P / 720P 两档并提示登录；用「获取Cookie」登录后才会放开更高档位（实际能拿到哪一档还取决于账号权限，失败时浮窗会给出提示）。浮窗内的**清晰度会被记住**（写入 `data/gui_rooms.json` 的 `ui.preview_quality`，下次启动优先于这里的 `quality`），**静音 / 音量 / 置顶只在本次运行内生效**，重启回到这里配置的默认值。
- 上述字段缺失、文件损坏、或写成 `"true"`（字符串）/数字等非布尔值时，一律按**默认值**处理（fail-safe；`emoticon_tooltip` 里字段名拼错也会整体回退默认）。程序启动时会在调试日志中显示写操作状态与日志落点。
- **升级后新增的配置项会自动补全**：默认配置只在文件不存在时生成，因此升级前就已存在的 `config.json` 拿不到后来新增的字段（例如新增 `medal_tasks` 时，文件里根本没有这一段，界面也就无法开启自动任务）。现改为**读取时就地补全**——只补缺失的键、**绝不覆盖你已有的值**（`true`/`false` 一律保留）、**空对象不填充**（`emoticon_tooltip: {}` 这类「显式关闭」的写法不会被补回默认开关），你自己加的键也保留；补全后会把文件内自动生成的 `_说明` 刷新为最新版本，并在调试日志中提示「已补全应用配置…」。

> ⚠️ **粉丝牌自动任务属于「自动向 B 站提交数据」的高风险操作**，可能触发平台风控甚至账号处罚。默认全部关闭，请充分评估风险后再自行开启。

## 自动检测浏览器里的直播间（--auto）

> ⚠️ **该功能为实验性实现，存在固有问题，推荐改用 GUI 启动方式（`start_gui.bat`）手动管理房间。**
>
> 当前实现是直接按字节扫描 Edge/Chrome 写到磁盘的**会话快照文件**，这带来一系列不可靠因素：
>
> - 依赖浏览器把标签页快照落盘的时机，刚打开的直播间最长要等一个扫描周期（30 秒）才能被发现；
> - 仅支持 Edge / Chrome（Chromium 目录结构），Firefox 等浏览器无法识别；
> - 已关闭但仍在 24 小时快照残留中的直播间会被**误包含**；
> - 快照格式属于浏览器内部实现，随版本更新可能变化导致功能失效；
> - 扫描得到的信息只有房间号，主播名等仍需额外接口查询。
>
> 相比之下，GUI 方式通过界面直接添加/启停/排序直播间，状态与标题实时更新，无上述问题。

`start_auto.bat`（或 `python main.py --auto`）的工作方式：

1. 扫描 Edge / Chrome 的会话快照文件（`User Data\<profile>\Sessions\` 下的 `Session_*`、`Tabs_*`），URL 在其中以明文存储，直接提取 `live.bilibili.com/<房间号>`；
2. 把检测到的直播间全部加入监听；已被其他实例监听的房间自动跳过（通过房间锁探测）；
3. 运行中每 30 秒重新扫描一次：浏览器里**新开的直播间自动加入**；已加入的房间不会因关闭标签页而停止，需手动停止程序（Ctrl+C 或关闭窗口）。

注意事项：

- 刚打开的标签页可能过几秒才被浏览器写入磁盘快照，最长等一个扫描周期（30 秒）即可被拾取；
- 已关闭但仍在最近 24 小时快照中的房间可能被误包含（快照是滚动覆盖的，通常很快消失）；
- 仅支持 Edge 和 Chrome（相同的 Chromium 目录结构）；Firefox 的会话为 lz4 压缩格式，暂不支持；
- 扫描只读浏览器文件，不需要关闭或重启浏览器，也不需要管理员权限。

## 图形界面（GUI）

双击 `start_gui.bat`，或 `python main.py --gui` / `python gui.py`。

**无控制台窗口启动**：`start_gui.bat` 启动 GUI 后不会保留黑色 cmd 窗口（日志看 GUI 的「调试」页签）；首次运行需要初始化虚拟环境时会短暂显示一个进度窗口，装完自动关闭。如果连首次初始化也不想看到窗口（例如加入开机自启），用 `start_gui_silent.vbs`——完全零窗口，但要求已经运行过一次 `start_gui.bat` 完成初始化。

- **直播间页签**：
  - 顶部输入房间号、直播间链接或**主播个人空间网址**（`space.bilibili.com/<uid>`）后点「添加」；
  - 房间列表实时显示监听状态与直播标题：除每次连接/重连自动刷新外，监听过程中收到开播（LIVE）、下播（PREPARING）、改标题（ROOM_CHANGE）弹幕推送时**实时更新**；
  - **排序手动触发**：工具栏可选「手动拖动 / 按房间号 / 按主播名 / 按直播状态」后点「排序」，可勾选「直播中置顶」；启动时按上次记忆的顺序显示，不再自动排序；
  - **拖动排序**：按住行上下拖动即可调整顺序，顺序自动记忆到 `gui_rooms.json`；
  - **多选批量操作**：按住 Ctrl（或 Shift）可选中多个直播间，一次批量开启/停用监听或删除；
  - **点击跳转**：单击房间号打开直播间，单击主播名打开主播个人空间（SC 中的用户名同样可点击跳转）；
  - 列分隔条可拖动调整列宽，拖宽后可通过列表下方的横向滚动条查看被裁切的内容；
  - 选中房间即在下方查看该房间的历史 SC（从磁盘 JSONL 读取，已退款的标灰注明）：切换即**默认加载最新 100 条**，滚动条/滚轮滚到顶部时自动加载更早的一页；顶部显示「已读取共 x 条历史记录」，每页边界处有「（已读取 x 条历史记录）」分割点（x 为触发该次加载时已读数量），历史区底部有「（历史 x 条sc记录）」分割线（切换直播间时已保存的历史 SC 总数），其下方为实时到达的新 SC；价格按额度着色（50/100/500 分档），底部始终显示当前房间的**「共 x 条SC记录」**；
  - 醒目留言标题栏显示房间号、主播、**直播标题（截断显示）**、**同接**（弹幕服务器推送的实时在线人数 `ONLINE_RANK_COUNT`，监听期间实时更新；注意 `get_info` 的 online 字段与"看过人数"均非同接，故不采用）与**舰长数**；
  - SC 视图与调试日志均支持**中键快速滚动**：按一下中键进入滚动模式，移动鼠标即快速翻动，再按一下中键/单击左键退出（类似浏览器）；
  - **开播提醒**：监听中的直播间从非直播中变为开播时，播放系统提示音并闪烁任务栏图标（不弹窗）；列表中的「提醒」列显示开/关，**单击该列即可切换**，保存在配置中。程序启动时已开播的房间不提醒；
  - **直播状态如何更新（高频开播也不会漏）**：以弹幕服务器的开播/下播推送为准——收到推送**立即**更新状态（不等接口），随后再查一次接口补齐标题等信息；因为 `get_info` 在开播/下播瞬间会返回**缓存**的旧状态，程序会用「推送状态有效期（约 30 秒）」把它纠正过来，过期后则以接口为准（避免一次丢失的推送把状态永久带偏）。此外每个房间约每 5 分钟做一次**周期性复核**兜底，即使推送漏收，状态也会自愈；重复的开播推送不会重复广播（不会重复提醒）。
  - **房间列表正下方**可编辑**备注**（回车或失焦保存）、**开启/停用监听**（停用即断开并释放房间锁）、**删除**（从列表移除，磁盘数据保留）；窗口最底部为**显示弹幕区**／**弹幕表情图**（Qt 版）开关与**刷新历史**／**获取Cookie**／**从插件获取**按钮。
- **房间独立窗口（右键房间行，ROADMAP 84）**：在房间列表里**右键某行 → 「打开独立窗口」**，即可单开一个只显示该直播间 **SC 区 + 弹幕区**的窗口（不含房间列表、粉丝牌、调试页签与工具栏），用于同时盯多个直播间而不用在主界面来回切换。**一房一窗、可同时开多个**：每个窗口各自绑定自己的直播间，主界面切到别的房间也不影响它；对同一房间再右键一次只把已有窗口**前置**，不会重复开窗。窗口内两区的能力与主界面相同——SC 的历史分页与「已读取共 x 条」标记、累计计数、吸底与「N 条新SC」徽标、点击用户名跳个人空间、退款 SC 置灰、头部（房间·主播·标题·同接·舰长·粉丝牌）；弹幕的点击正文复制、右键回复/@、表情面板与点选发送、发送弹幕（含颜色/模式）、悬浮看原图（Qt 版表情图直接显示在弹幕流里）、未读徽标与 4000 行裁剪。**Qt 版窗口底部同样有「弹幕表情图」开关**，与主界面底部是**同一个全局开关**：任一处切换都会立刻作用于主界面与所有独立窗口。窗口行为：**不抢主窗口焦点、不置顶**；**按房间记住位置与尺寸**（写入 `data/gui_rooms.json` 的 `ui.room_windows`，下次打开沿用——只恢复几何，**不会自动重开窗口**）；关闭主程序时一并回收；**房间被删除时自动关闭**。发弹幕 / 表情包同样受 `config.json` 的 `allow_write_operations` 与登录态约束。
- **弹幕区**：窗口最底部的「弹幕」开关开启后，在 SC 区下方实时显示**当前选中房间**的弹幕（时间 + 用户名 + 内容，每轮轮询批量渲染）。窗口最大化时弹幕区挤占 SC 空间；窗口化时窗口自动向下扩展、关闭时还原。弹幕按日写入 `room_<房间号>/dm_YYYYMMDD.jsonl`（仅开关开启期间的选中房间落盘；内容含用户昵称，注意隐私）。弹幕区只保留**最近约 4000 行**（超出自动裁掉最旧的一半，避免长时间直播后界面越来越卡；完整内容都在落盘文件里）。弹幕列表下方提供**发送弹幕**与**发送表情包**（见下）。
  - **点击弹幕**：单击**用户名**跳转其个人空间；单击**正文文字**把该条弹幕文本复制到剪贴板，并在发送区下方短暂显示「已复制：…」（点时间、用户名或正文右侧的空白处都不会触发复制）；**右键**「回复该弹幕 / @ 该用户」。
  - **新消息提示**：向上翻阅历史（滚动条不在最底部）时，SC 区/弹幕区**右下角会出现可点击徽标**「N 条新SC ↓」「N 条新弹幕 ↓」，点击即回到底部并恢复自动跟随；手动滚回底部后计数自动清零。SC 区行为一致。
  - **弹幕表情（两版呈现方式不同）**：整条都是表情的弹幕，**Tk 版**显示为「[触发词]」、靠鼠标悬浮 0.5 秒看原图（实测直播间表情占比常超 50%，Tk 的 `Text` + `PhotoImage` 内嵌图片会随历史弹幕量把界面卡死）；**Qt 版直接把表情图片显示在弹幕流里**——图未下载完先显示触发词，图片就绪后**原地换图**（只改该行的一段，滚动位置不受影响），点击图片同样能复制该条弹幕、右键同样能回复。两版的**悬浮提示**都只显示 `emoticon_tooltip` 配置里的文字字段（默认触发词），Qt 版不再重复弹一张大图（图已在弹幕里）。落盘文件里始终是 `[触发词]` 文本。
  - **「弹幕表情图」开关（Qt 版，窗口底部）**：内嵌表情图更直观，但一行会明显变高（表情图高 40~64px，纯文字行只有约 23px），弹幕密集时占掉不少高度。这个开关默认开启，**两个方向都立刻作用于已有弹幕**：关闭后弹幕流只显示「[触发词]」文字，**已经显示的表情图会被还原成文字**（不必等新弹幕，行高马上降下来）；**重新开启则把弹幕里已有的触发词换回图片**（图仍在缓存就直接换，否则先触发下载、图片到位后自动补上），无需切房重载。为控制开销，只处理**最近约 400 条表情弹幕**（更早的已滚出视野，不再追溯）。关闭期间悬浮提示恢复为「有原图就看原图」的行为（弹幕里已经没有图了）。开关状态记在 `data/gui_rooms.json` 的 `ui.dm_emoticon_image`，下次启动沿用。
  - **悬浮提示**：鼠标在**表情面板**或**弹幕区表情**上停留约 0.5 秒，弹出不抢焦点的小提示（鼠标移开、换页、切房、退出即消失）；提示内容由 `config.json` 的 `emoticon_tooltip` 决定，**默认仅触发词**，可另外显示 `unique`（唯一标识）与数字 `id`。
- **发送弹幕 / 表情包（写操作，默认关闭）**：需先把项目根目录 `config.json` 的 `allow_write_operations` 改为 `true`（默认 `false`，见上文「应用配置文件」），并通过「获取Cookie」取得**已登录**的 B 站 Cookie（须含 `bili_jct`），二者都满足后输入行与「表情」按钮才可用。满足后在弹幕区底部输入内容，回车或点「发送」即可发到当前选中房间；可先选择弹幕**颜色**与**展示模式**（滚动/顶部/底部）；候选会随所选直播间刷新为**服务端实际可用项**（账号只支持 1 项时下拉就只有 1 项，属正常），仅查询失败时才回退为内置候选。点「表情」按钮在**发送行上方展开当前直播间的专属表情面板**（再点一次、「收起」或 Esc 收起，切换直播间自动收起，不另开窗口）：**按表情包分页（一页 = 一个表情包）**，可「◀ 上一包 / 下一包 ▶」或从下拉框直接跳页；表情**固定一行展示、面板高度恒定**（约 155px，不随表情数量变化），一页表情放不下时**横向滚动**（横向滚动条常显，滚轮也可横向翻动）；**点击表情即发送**（与网页端一致；面板发送后保持展开，可连续挑选；**按直播间分别记住浏览到的表情包**（翻页即写入 `data/gui_rooms.json`，面板开着直接退出程序也不会丢，重启后仍生效），再次展开即回到该包；**每次展开都会刷新可用表情包**（同一房间 30 秒冷却），粉丝灯牌升级等新解锁的表情包下次展开即可同步，且会停在你原本浏览的那个包；表情图片按**原始大小 1:1** 显示（不做缩放，像素清晰；仅超过 260×72 的异常大图才会等比缩小）；异步加载并缓存，格式不受支持时回退为「[触发词]」按钮）。客户端**不再做字数限制、重复内容拦截与发送前二次确认**（输入后回车/点「发送」直接发出，长度与重复由服务端判定）；为避免误触与风控仍保留：同一房间 **2 秒发送冷却**、发送中防连点、空内容拦截；失败按 B 站返回码提示（未登录 / csrf 校验失败 / 超长 / 频率过快 / 风控等）。程序**不会自动发送、不会自动重试**。
- **直播预览（仅 Qt 版，ROADMAP 63）**：点工具栏「**预览**」在**独立浮窗**里播放所选直播间的直播流——也可以在房间列表里**右键房间行** → 「预览该房间 / 停止预览该房间 / 设为主路」（右键非选中房间时会顺手选中它，保证预览与下方 SC / 弹幕面板一致）。**可同时预览多路**（最多 4 路，见 `preview.max_rooms`）：Ctrl 多选后点「预览」即批量加入，**双击房间行**也能直接加入/停止该房间的预览（跳转列除外，避免与单击打开浏览器打架——排序栏有提示）；浮窗内按路数自动排**宫格**（1 路全屏、2 路左右分栏、3~4 路 2×2），**点某一格把它设为主路**——只有主路出声（其余强制静音，避免多路声音混在一起），**双击某一格可放大**（再双击还原；放大时若该路被停掉会自动退出放大），每格右下「✕」停掉该路（停掉后其余格子立刻重排，不留黑框）。为多路加了**资源保护**：副路卡住只自动重连 1 次，仍不行就停掉这一路；进程 CPU 连续约一分钟偏高（>70%）时也会自动停掉最后加入的副路——多路预览是「扫一眼」，不值得为了看不到的画面把整机拖垮。浮窗可缩放、置顶、拖到任意位置，与主窗口互不干扰。浮窗内的按钮是**暂停 / 继续**（作用于主路）——暂停只**定格当前画面**（预览仍在进行、本地代理不释放，可继续换清晰度），点「继续」恢复直播（若暂停太久、流已断开，会自动重新拉流）。**结束预览**请用工具栏「停止预览」、右键菜单「停止预览」，或直接关掉浮窗：三者都会停止播放、释放本地代理并**关闭浮窗**；程序退出时也会自动收窗。浮窗内可**暂停 / 继续**、**刷新**、切换**清晰度**、**静音**与调节**音量**，并显示当前状态（拉流中 / 播放中 · 清晰度 · 格式 / 已暂停 / 失败原因）。注意直播流没有"跳到最新"的通用手段：**暂停后继续是接着暂停处播**，反复暂停会让画面越来越晚于真实直播——**点「刷新」可立刻追回**（暂停超过 30 秒再继续时也会自动刷新一次）。清晰度是**全局**的（作用于所有路；各房间可用档位不同时按该房间可用最高档播放，格子标题显示该路**实际**档位），**默认「自动」**（首次播放直接取该房间可用最高档，例如「原画」）；下拉只列**该房间真正可用**的档位（来自新版拉流接口 `getRoomPlayInfo` 的 `accept_qn`——该房间没有 4K/杜比就不会出现这些项；名称与 B 站一致、**不带分辨率**，因为同一档位在不同房间的分辨率并不固定）。**未登录只能看 720P**（B 站对匿名请求的限制），此时下拉只有 360P / 720P 并提示登录。若你选的档位该房间不支持，会自动**回退到可用最高档**并提示后重新拉流；选「自动（最高）」则始终跟随房间能力。**切换清晰度会自动重新装载**（无需手动停止再播放）。默认**静音**、默认**置顶**、默认**跟随**主界面选中的直播间——但**只切换「主路」的声音**，绝不增删或替换预览内容（选中的房间已在预览中→它变成有声音的那一路；不在预览中→什么都不做）。**加密（密码）直播间**：拉流前会先确认该房间是否加密——是加密房且尚未解锁时，格子里会提示，**右键该格 → 「输入密码…」**输入密码即可（密码**只存在内存里**：切房 / 停止预览 / 退出程序即丢弃，不写入任何配置文件）。提交后会先在服务端校验一次，再带着密码重拉。**失败提示会翻成人话**：未开播提示「开播后点刷新即可」、风控提示稍后再试或重新获取 Cookie、网络异常提示检查网络，而不是甩一串错误码。**清晰度会被记住**：在浮窗里改过的档位写入 `data/gui_rooms.json` 的 `ui.preview_quality`，下次启动沿用（此前只在本次运行内有效）。**越看越落后会自动追回**：实测直播播放比网页端每分钟约慢 0.1~0.2 秒（播放端固有小幅落后，与本地代理转发无关），累计到 `preview.max_drift_sec`（默认 3 秒）就自动重新拉流跳到最新画面，并提示「已落后 X 秒，正在追到最新画面…」——一次短暂重载换回同步，随后重新开始测量（把该值写 `0` 可关闭此行为）。**播放中断会自动重连**：每 5 秒检查一次（预览进行中、未暂停、窗口可见、主播在播，播放器却停住了——直播流连接被断开或直链过期时可能连错误都不报，画面直接定格），自动重新拉流换源并提示「播放中断，正在自动重连（第 N 次）…」；**主路**连续 3 次仍未恢复就停下来提示你点「刷新」，**副路**只重试 1 次就直接停掉这一路（把资源让给主路）（刚换档 / 换源后的 15 秒内不判定，避免把起播缓冲误当成断流；主动暂停、窗口隐藏、主播未开播都不算断流）。**可选：上报观看时长**（`webHeartBeat`，写操作，**默认关闭**）——在浮窗里勾选「上报观看时长」后，预览播放期间会按服务端给的节奏（约每分钟）上报一次网页端观看心跳，让账号在预览的直播间累计观看时长，开关旁显示「已上报 mm:ss」。它要求 `config.json` 的 `preview.watch_time` 与 `allow_write_operations` **都**为 `true`，并且已登录（点「获取Cookie」）；三者缺一时勾选会被拒绝，原因显示在开关旁。只在你**真正在看**的时候上报（正在播放 + 未暂停 + 主播在播；暂停 / 缓冲 / 断流 / 未开播都不计，切房按新房间重新累计），上报失败会立即停止并提示、不自动重试。**这是模拟网页端行为的高风险操作，可能触发风控，请自行评估后再开启。**
  预览的**每个动作都有日志**（可在「调试」页查看：默认级别就能看到「加入预览第 2 路」「开始播放（HLS，原画）」「预览落后 3.2 秒，自动追到最新画面」「停止预览第 1 路」等；勾选「显示 DEBUG 日志」还能看到每次定时换源、每路状态变化、流就绪是「重新装载」还是「仅换上游」等细节）。日志按区块归类：**播放 / 连接类**（起播、重连、追边、断流、密码、观看时长上报）归 `live`，**界面类**（加入 / 移除路、主路切换、清晰度、静音、置顶、暂停、窗口显示）归 `window`；接口请求（拉流信息、直链、密码校验）归 `data`，可在 `config.json` 的 `logging.categories` 里按需关闭。
  实现上**不直接连 B 站直链**：直链带防盗链（缺 `Referer` 会 403），而播放器又无法自定义请求头，所以程序在本机回环地址起一个**临时转发代理**（随机端口、只监听 127.0.0.1、不对外暴露）代注入请求头，播放器只连本机地址；HLS 的分片地址也会改写到代理，否则播放器直连分片照样 403。**HLS 优先**（播放列表由代理逐次转发，直链过期换源无需重连），直链到期前每 10 分钟自动换新地址，播放出错自动换另一种格式（HLS ⇄ FLV）重试一次。Tk 版没有可用的视频组件，暂不提供该功能。
- **调试页签**：程序运行日志，每条日志带 `Room[房间号]` 前缀，可区分不同房间（如"已接入（房间号）直播间""收到 SC（房间 xxx）"），勾选后显示 DEBUG 级别（含所有弹幕消息类型与人气值）。**同一份日志可选写入 `logs/app.log`**（见上文「应用配置文件」的 `logging` 段：把 `enabled` 改为 `true` 即开启，级别 / 路径 / 轮转也可配置，默认 2 MB × 3 个备份），静默启动（`start_gui_silent.vbs`）时即可事后查看运行状态。
- 房间列表、备注、启停状态、排序/音效等界面偏好，以及**每个直播间上次浏览的表情包**，都保存在 `data/gui_rooms.json`（表情包记忆在 `emoticon` 段，形如 `{"1": {"index": 1, "name": "房间专属"}}`；**Qt 版还会记住上次的窗口尺寸**（`ui.window_size`）与**上次选的预览清晰度**（`ui.preview_quality`），下次启动自动恢复；预览里的加密房间密码**不会**写入任何文件）。
- GUI 与命令行实例共用房间锁：同一房间同一时间只会被一处监听，重复启动会显示"被占用"。

## 粉丝牌任务

「粉丝牌」页签集中展示**你持有的粉丝牌**与**各监听房间的每日任务进度**，并可为单个房间手动或自动完成其中的写任务（点赞、发弹幕）。

- **获取等级与任务（只读）**：需先用「获取Cookie」取得**已登录**的 B 站 Cookie（含 `SESSDATA`，写操作另需 `bili_jct`）。程序**启动时自动拉取一次**粉丝牌与任务，无需先点开「粉丝牌」页签。
  - 「刷新粉丝牌」拉取账号全部粉丝牌（勋章名、等级、主播、房间、是否点亮/直播中），分页拉取并按勋章去重；亲密度拆成两列——**「今日亲密度」为今日已获取**（`+23`），**「当前/升级需」为当前亲密度 / 升到下一级所需经验**（如 `26/99`）；
  - 「刷新任务」逐房间拉取任务清单，界面显示「当前/上限」与是否完成；**未持有该主播粉丝牌的直播间显示「无粉丝牌」并跳过请求**（不会一直卡在「正在刷新」）；**任务上限随粉丝牌等级提升而上升、每日刷新，一律以接口返回为准**（程序不写死数值）；
  - 选中房间后，醒目留言标题栏会显示该直播间的**粉丝牌名称与等级**（在「同接」「舰长」之后，如「小路泥 Lv12」；未持有时不显示）。
- **任务清单**：常见为**观看直播满15分钟、发弹幕、点赞**等；其中「观看直播」**仅展示进度，不自动挂机**（保持只读）。
- **未点亮/不适用任务会跳过**：粉丝牌未点亮时任务显示「仅点亮」（无进度上限），此时**不执行**点赞/发弹幕、也**不空发请求**；「一键完成」只处理真正有进度、可执行的任务。
- **顺序跟随直播间列表**：「监听房间 · 任务」列表的行顺序**与直播间页签完全一致**，且**实时跟随**——在直播间页按房间号/主播名/直播状态排序、勾选「直播中置顶」、拖动调整顺序、添加或删除直播间后，粉丝牌页立刻同步同样的顺序（本页不单独排序）。
- **自动刷新（无需手动点）**：执行任务期间，引擎每轮复核后**实时上报进度**并就地更新对应行；任务完成后自动刷新粉丝牌列表与任务；停留在「粉丝牌」页签时每约 **90 秒**静默刷新一次（粉丝牌列表 + 各房间任务，切走即停止），因此亲密度/经验与任务进度会自动跟随（含在浏览器里产生的进展）。
- **执行效率可观测**：每次执行后在页签提示与调试日志中给出**请求次数与进度变化、发送条数（表情 / 文本）、单任务用时与总耗时**，便于评估节奏（如「点赞：…（5 次请求，进度 5→10，用时 38.6s）」）。
- **分任务执行按钮（按房间）**：选中某房间后，「**发弹幕（选中房间）**」「**点赞（选中房间）**」是**两个独立按钮**（顺序与上方任务列表列顺序一致），各自只执行对应任务、且**只作用于该房间**（不会触发其它直播间，也不会连带执行另一项）。任务不存在/已完成/未点亮时会在提示区给出原因。
- **点击跳转（含点击保护）**：两张表里的**主播**（粉丝牌列表、任务列表）与**房间号**均可单击跳转——主播 → 个人空间、房间 → 直播间。与直播间页签一致：跳转列**按下时不改变选中行**、**松开且未拖动**才真正打开链接（避免拖动列宽/误触时误开浏览器）；任务列表在主播 uid 未知时会先后台补齐。
- **表格列宽**：两张表都支持拖动列分隔条调整宽度（拖动稳定、不互相挤压），列总宽超出窗口时底部有**横向滚动条**可查看被裁切内容。
- **自动完成（按房间、按任务，可选）**：**「自动发弹幕（选中房间）」与「自动点赞（选中房间）」是两个独立开关**，各自只自动执行对应任务（可只开一项）；程序每约 5 分钟为该房间补做已开启且未完成的任务（**同一房间两项都开时，在同一次执行里依次完成**——否则后一项会被「该房间正在执行中」长期挡住）。自动执行需同时满足：`allow_write_operations=true` + `config.json` 的 `medal_tasks.auto=true` + 该房间已勾选对应开关；任一不满足都只提示、不执行。任务列表的「自动」列显示该房间已开启的项（`弹` / `赞` / `赞+弹` / `关`）。
  - **自动发弹幕默认只在未开播时执行**（避免在直播弹幕区刷屏）：需另勾「**允许开播时自动发弹幕**」才会在开播（直播中）时也执行；该开关同样按房间独立，且需先勾「自动发弹幕」才生效。**手动**「发弹幕」按钮不受此限制（随时可点）。
- **发弹幕内容**：默认**轮次循环发送该直播间专属表情包**；若该直播间**没有专属表情包**，回退发送**纯数字文本**（`1`、`2`、`3`……递增）。
- **完成即停**：以接口返回的 `已完成` 或「当前 >= 上限」为唯一停止判据，执行后重新拉取复核，达标立即停止，不做补齐式重发。
- **按轮次推进（重要）**：实测服务端对**点赞计数有节流/延迟**，单次请求通常只推进约 1 点进度，且 `click_time` 大小不保证等量计入。因此点赞会**按随机间隔多轮发送**直到进度达上限（`limit` 为 10 时约需 5~10 轮，按默认 15~20s 间隔可能需要数分钟）；发弹幕同理按轮次推进。**连续无进展/失败达上限**（`medal_tasks.max_retry`）即停止本轮，留待下次或自动任务下一轮继续——不是失败，也不会无限空发。
- **节流与风控**：点赞与发弹幕按房间串行、动作之间随机间隔（默认点赞 15~20s、弹幕 6~8s，可在 `medal_tasks` 调整）；点赞仅在**直播间开播时**执行；命中风控码立即中止并提示，**不做失败重试风暴**。

> ⚠️ **风险提示**：自动点赞/发弹幕属于违反平台常规使用方式的高风险操作，可能触发风控甚至账号处罚；这是本项目「不会自动发送、不会自动重试」原则的**显式例外**，且默认全部关闭。请自行评估后谨慎开启，并控制使用频率。

## 原理简述

1. `room/v1/Room/get_info` 把短号换算成真实房间号；
2. `xlive/web-room/v1/index/getDanmuInfo`（带 WBI 签名和 buvid3 cookie）取弹幕服务器列表和 token；
3. 连接 `wss://<host>:<wss_port>/sub`，发送认证包 `{"uid":0,"roomid":...,"protover":3,"platform":"web","type":2,"key":token,"buvid":...}`；
4. 每 20 秒发一次心跳，并以 5 秒为周期检查应答；普通消息（op=5）为 brotli 压缩的 JSON 流，其中 `cmd=SUPER_CHAT_MESSAGE` 即 SC；
5. 心跳超时（45 秒无应答）/ 连接断开后自动重连，重连前重新获取 token；等待时间按指数退避并叠加 ±30% 随机抖动（1 秒起、30 秒封顶），握手成功后重置。

## 多开说明

- 监听多个房间**不需要多开**：单实例原生支持 `python main.py 房间1 房间2 房间3`，这是推荐方式。
- 不同房间可以多开多个实例，共用 `data` 目录也安全（数据按 `room_<房间号>/` 目录天然隔离）；想更清晰也可以各用 `-o` 指定不同目录。
- **同一个房间同一时间只允许一个实例监听**：解析出真实房间号后程序会在 `room_<房间号>/.room_lock` 上加互斥锁，第二个实例会报错并停止该房间，避免并发写同一批文件导致记录重复、损坏。锁随进程退出（含崩溃）由操作系统自动释放，不存在残留死锁；磁盘上留下的 `.room_lock` 文件是正常的持有者信息记录，删不删都不影响下次启动。
- **无需拷贝项目文件夹**：单目录即可多开——代码与虚拟环境只读共享，数据按 `room_<房间号>/` 目录隔离。复制 `start_room_模板.bat` 制作双击启动脚本（含房间号的脚本不入库），或在命令行执行 `start "实例名" run_with_venv.bat 房间号`。
